第 1 课 · 10 分钟

从员工提问到有引用的答案

这一课，帮你建立起构建可靠企业 RAG 聊天机器人的第一个心智模型。

本课的实际收获

本课的实际收获： 看到一个答案出了问题，你能马上判断是检索没找对证据，还是生成环节没写好——这个判断决定了接下来该动哪里。

1 · 一句话说清 RAG

检索增强生成（RAG）说白了就是：用户一提问，系统立刻从公司知识库里挑出相关证据，塞进模型的上下文，再让模型照着这些证据给出有依据的答案。

这跟把所有 SOP 永久“教”给模型完全是两回事——模型每次看到的，只是为这一次请求挑出来的证据。也就是说，聊天机器人可能在模型动笔之前就已经出错了：检索错了文档、切错了文本块，或者压根没捞到有用的证据。

在受监管、要接受审计的场景里，“听起来靠谱”从来不是质量标准。答案必须有正确的证据撑腰，而且要标出处。

首选阅读：OpenAI 的《优化 LLM 准确度》指南——目前只需阅读其中关于 RAG 的部分。

2 · 你实际使用的系统

你在 demo 目录下的演示环境是我们安全的沙盒：25 份虚构的 Meridian Labs 文档和 65 个问题，其中 6 个问题系统应该直接拒答。

问题
“Quel est le délai de clôture d’un plan d’action pour une non-conformité majeure ?”

1. 检索 → Qdrant 语义分块 + Qdrant 摘要 + Meilisearch 关键词命中 + LightRAG 上下文

2. 组装 → `qa_service.py` 合并并截断证据

3. 生成 → 由生成模型根据组装好的上下文写出答案

4. 引用 → 从实际展示给模型的上下文条目中提取来源

5. 评估 → `demo/eval.py` 分别给检索、答案正确性、引用、拒答、幻觉和延迟打分

这种分层思维是整门课程的地基——演示报告可不只是给一个百分比，它会告诉你系统到底薄弱在哪个环节。

3 · 先诊断，再改代码

观察到的现象可能出问题的层级首先该检查的地方
`/api/v1/search` 里缺少预期文档检索索引、分块、查询形式、阈值、排序
预期文档已检索到，但没有被引用上下文/引用组装上下文截断与来源提取
文档已引用，但答案遗漏了必要事实生成提示词、上下文组织方式、模型行为
答不了的问题却给出了自信的回答有依据/安全拒答指令、证据阈值、评估集
答案正确但响应缓慢运维后端延迟、图检索调用、上下文大小、并发

4 · 练习：是检索问题还是生成问题？

场景 A： 答案说是“24 小时”——可 `/api/v1/search` 根本没返回 `PR-QA-MRD-009`。先出问题的是哪一层？

场景 B： `PR-QA-MRD-009` 明明就在搜索结果里，但答案说“60 天”，证据写的却是“45 天”。这是哪里出了问题？

场景 C： 一个本来答不了的问题，系统却给出一段详细又自信的回答，还没标来源。哪个指标应该揪出这个问题？

5 · 你的原型成功标准

你的原型成功标准：继续做实验之前，先用自己的话把下面这五个目标写清楚。

  1. 哪些问题类别是必须优先保证跑通的？
  2. 第一版 MVP 需要达到什么样的准确率门槛？
  3. 可以接受的最低来源命中率是多少？
  4. 什么样的幻觉率是不能接受的？
  5. 真实员工能够容忍的响应时间是多久？

别直接把历史报告 `demo-fixed` 里的数字照搬当成自己的目标。那些数字只是拿来讨论的基线，不代表现在的系统已经能上生产。

与课程使命的关系

你的用户是 QA 团队、监管机构、供应商、审计员——这些人不在乎答案说得多漂亮，他们在乎的是能不能对照正确的 SOP、政策或问卷核实。这就是为什么我们的第一个工程习惯是这样的：

答案出错时，先查检索出来的证据，别急着改提示词。

下一步行动

下一步： 在脱敏的演示环境里跑一遍离线检查，然后去看评估报告。

cd demo
python eval.py verify
python test_scoring.py

然后打开现有报告 demo-fixed.md，找出两个失败案例：一个是检索成功但答案仍然部分错误或完全错误，另一个是某个来源根本没有被检索到。

如果哪个术语、指标或失败案例还没弄懂，尽管接着问我。 下一课，我们会拿一个真实问题，顺着实际代码和评估工具走一遍完整流程。
