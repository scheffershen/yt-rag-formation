第 05 课 · 20–30 分钟，另加运行时间

语义检索、关键词检索、图谱遍历与混合检索

在把一个系统称为"混合"之前，先量化它的每个检索信号——向量、全文/词法、摘要、图谱——到底各贡献了多少。

本课的具体收获

学完本课，你会填好一张逐题对比表，并选定一项有证据支持的检索改进方向。

1 · 最小可用模型

  • 向量检索（语义）： 把文本转换成浮点向量（例如 Qdrant、Pinecone），用来捕捉高维相似度、上下文、含义和改写表达，而不是精确字词。它在跨语言场景下的表现取决于所用的嵌入模型——不要假设，要实测。
  • 全文检索（词法）： 用 BM25 等算法和容错拼写匹配字面词元、精确标识符、名称、缩写和数字（例如 Meilisearch、Elasticsearch）。当精确拼写本身承载含义时，靠的就是它。注：引擎的边界正在演变——像 Meilisearch 这样的引擎也能原生处理向量嵌入，实现统一的混合检索。
  • 图检索（关系型/结构化）： 动态遍历显式的节点、边和实体关系（例如 Neo4j、LightRAG）。它不只是"另一种找分块的方式"——它是唯一能可靠完成多跳关联追溯的结构化信号（例如把分散在不同文档中的事实连接起来），这是向量检索和全文检索单独都做不到的。
  • 摘要检索： 一个独立索引，为每一整篇文档保存一条向量化摘要，而不是按分块保存。它是为"这份文档讲的是什么"这类问题设计的——当一个约 500 token 的分块作为单位太窄，装不下整篇文档时。
  • 累计并集： 在这个实验里，只要一个来源出现在四个信号中的任意一个里，就算被找到。这能说明检索的贡献，但完全说明不了最终答案是否正确。
  • 混合检索： 在这套系统里，"混合"指的是让所有信号并行运行，再把各自格式化后的结果拼接进提示词——而不是把它们融合或重排。跨信号之间没有分数归一化，也没有倒数排序融合（reciprocal rank fusion）；真正的融合只发生在 LightRAG 内部，在它自己的实体、关系和向量三路之间。代码库里存在一个重排引擎，但没有接入线上检索——不要以为"混合"就意味着比"并行拼接"更复杂精巧。

首选阅读：Qdrant Hybrid Search——留意它如何组合多种检索表示，以及为什么这种组合需要实测验证，而不能想当然认为有效。

2 · 跑一次受控实验

复用第 4 课那套隔离演示环境和评估集。检索模式直接命中 /api/v1/search，不经过大模型评判环节，这样才能干净地只看检索本身。

cd demo
python3 eval.py verify
python3 eval.py run --mode retrieval --workspace meridian_demo --tag lesson-05-experiment

这会生成两个文件：一份汇总报告，一份逐题 JSON 报告。

reports/lesson-05-experiment.md
reports/lesson-05-experiment.json

对每一道你要检查的题目，看这些字段：

  • results[].retrieval.indexes.vector.all
  • results[].retrieval.indexes.fulltext.all
  • results[].retrieval.indexes.summary.all
  • results[].retrieval.indexes.graph.all
  • results[].retrieval.cumulative["vector+fulltext"].all
  • results[].retrieval.cumulative["vector+fulltext+summary"].all
  • results[].retrieval.cumulative["vector+fulltext+summary+graph"].all

判断命中要看来源元数据，而不是看文本是否碰巧出现——一个文档 ID 只是在另一篇文档正文里被提到，不算作一次检索命中。

图谱这一列本身就是近似值，报告里也说明了这一点：LightRAG 返回的是一整段扁平的上下文字符串，而不是一份文档列表，所以只要引用出现在这段字符串的任何位置，就算作图谱命中——这有可能来自另一篇文档内部的交叉引用，而不是目标文档本身。把它当作一个真实但更嘈杂的信号看待。它是单独报告的，绝不会被悄悄并入其它三个信号。

与课程使命的关系

面向受监管企业的聊天机器人，两头都得做对——既要精确措辞的流程查找，也要像真人一样提问的政策类问题。这张表，正是把这个可靠性目标，变成一个真正可追溯的检索决策。
