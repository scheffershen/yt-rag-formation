第 09 课 · 25–35 分钟

上下文组装与证据预算

检索到的结果不会原封不动地进到模型的上下文里——排序、截断、重复，随便一个都可能在你没留神的时候，把辛苦找到的证据悄悄挤掉。这节课教你怎么在丢证据之前就发现问题。

本课的具体收获

画一份多跳问题的证据存活地图，再给出一条站得住脚、有边界的上下文预算建议。

1 · 核心技能

拿 q30 或 q63 来练手，把它从头到尾走一遍——从检索挖出的来源，到上下文组装，一路到提示词预算。

  • 上下文组装：把后端结果变成真正喂给回答模型看的那段文字。这个系统里，这一步分四路信号——摘要、向量、全文、图谱——build_context() 会用最大最小公平算法，在一份字符预算中给每个有内容的通道分配份额。它尽量按完整条目丢弃检索结果，报告哪些证据留了下来，并避免某一路被饿到零而另一路还有富余。摘要、向量和全文的每个条目最多 1,200 个字符；图谱上下文最多 6,000 个字符；合并后的 max_context_chars 默认是 32,000 个字符（可配置范围为 1,000–50,000）。
  • 分块大小与上下文预算不是一回事：前面发现的统一索引器对 Qdrant/Meilisearch/摘要使用 500 token 分块，对 LightRAG 使用 1,200 token 分块。这些是建索引时的 token 大小，不是回答模型的字符预算。把 500 改成 800 需要重新建索引；它本身不会改变 build_context() 的回答上下文上限。
  • 证据预算：你能负担得起的上下文上限，由字符数、token 数、延迟或成本说了算。
  • 来源存活率：格式化、截断做完之后，某条证据是不是还留在最终的上下文里。代码里描述旧做法的注释说得很直白：以前是固定顺序拼接，"决定谁能进上下文的是位置，不是相关性"，图谱这一块总排在最后，所以永远是第一个被挤掉的。
  • 这跟第 5–8 课走的不是同一条路：那几课的 --mode retrieval 打的是 /api/v1/search，没有任何融合，纯拼接；这一课的 --mode answer 打的是 /api/v1/qa，才有真正按信号公平分配预算的逻辑。第 8 课学到的"没有融合"，搬到这一课不适用。

首选阅读：Anthropic — Contextual Retrieval

2 · 运行证据闭环

cd demo
python3 eval.py run --mode answer --workspace meridian_demo --category multi_hop --tag lesson-09-context

把命令、配置、结果和失败案例都记下来；别拿一次实验的结果，就断定整个系统已经靠谱了。每一条证据都去看报告里的这几个字段，别靠猜：

  • results[].answer.stats.context_chars_by_index——摘要/向量/全文/图谱各自有多少字符真正进了提示词。
  • results[].answer.stats.max_context_chars——合并后的字符预算；当前 API 默认是 32000，不要把它和建索引时的 chunk size 混为一谈。
  • results[].answer.stats.context_items_included 和 .context_items_dropped——后者只有真被丢弃的信号才会出现，按信号分别列出。
  • results[].answer.stats.context_hard_truncated——正常应该不存在或是 false，一旦是 true，说明公平分配的兜底逻辑不得不从字符串中间硬切——设计上这本该是永远不会发生的情况。
  • results[].answer.sources 和 .source_hit.all——真正留存下来的引用，以及是不是覆盖了所有预期来源。

如果截断在生成之前就把某个来源删掉了，模型根本不会看到它——检索阶段找到过这件事本身不算数。多跳问题尤其要先看 context_chars_by_index.graph，再看 graph 有没有出现在 context_items_dropped 里——这能告诉你连接两个事实的证据到底有没有活着进入提示词，别急着下结论说模型推理能力不行。

与课程使命的关系

模型压根没看到的证据，系统没法引用。检索明明做对了，答案却可能就在上下文组装这一步，悄悄变成半吊子回答，甚至是幻觉。
