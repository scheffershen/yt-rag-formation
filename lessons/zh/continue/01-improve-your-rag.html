继续学习 · 01 · 生产环境改进闭环

把每一次 RAG 交互都变成更好的下一个版本

先给应用打点埋点，倾听用户反馈，再把真实证据交给 Claude Code 或 Codex——而不是含糊地要求"把 RAG 做好一点"。

本课的具体收获

交互 → 日志 → 用户反馈 → Agent 分析 → 改进计划 → 界定范围的修复 → 新证据。产出的是一份站得住脚的计划，而不是一堆猜测。

1 · 先记录每一次交互，再调整任何东西

对每一个回答，保存稳定的交互 ID、用户与入口、准确的问题、请求参数、按通道检索到的文档、最终上下文、回答、引用、延迟、成本和错误。

没有追溯记录的坏答案只是一则轶事。带着追溯记录的坏答案才是一个工程案例。

2 · 把反馈记在同一条记录上

在每个回答下方加一个赞/踩按钮，附带可选评论。把评分、评论和时间写回那条交互 ID。反馈告诉你哪些失败真正要紧；日志告诉你系统实际做了什么。

3 · 把真实日志交给 Claude Code 或 Codex

抽取 20-30 条差评记录。脱敏之后，提供查询内容、按通道的结果、上下文、回答、引用、延迟和评论。让 Agent 把每个失败归类为 retrieval_miss、ranking_miss、unfaithful_answer、over_refusal、under_refusal 或 followup_lost。

分析这些差评交互记录。
对每一条，指出一个失败类别，并引用日志中的证据。
把重复出现的模式归为一组。暂时不要提出修复方案。
如果证据不足，说明日志里缺了哪个字段。

4 · 索要一份计划，再界定一个修复范围

把归类好的这批数据交还给 Claude Code 或 Codex。要求给出一份按优先级排序的计划，把每一项改动与其证据、责任层、预期的指标变化、回归用例和验证方法关联起来。先从影响最大、改动最小的修复开始。

根据这些已归类的日志，提出一份按优先级排序的 RAG 改进计划。
每一项包含：证据、责任层、改动内容、风险、验收标准、回归测试，以及基于新日志的验证方式。
不要改动无关的检索通道或生成提示词。

5 · 按保持证据完整的顺序推进改进

  1. 先让日志和反馈变得可靠。
  2. 在责任层里修复一个已测量到的失败类别。
  3. 从一次真实交互中加入一个回归用例。
  4. 发布这个界定范围的改动。
  5. 在新日志上重新跑同样的分析，比较数量变化。

交付物

一份与生产环境证据挂钩的、按优先级排序的 RAG 改进计划，每个提议的修复都配有一个回归用例，发布后还有明确的重新分析步骤。

下一步行动：在再多花一个小时调整提示词或向量嵌入之前，先把交互日志和反馈控件加上。
