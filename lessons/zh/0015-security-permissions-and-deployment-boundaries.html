第 15 课 · 25–35 分钟

安全、权限与部署边界

秘密、数据、租户边界，光在文档里写"安全"两个字没用，得真去验证过才算数。

本课的具体收获

做一份 MVP 级别的威胁与权限清单，每条边界都配一个负向测试，证明它真的挡得住。

1 · 这项技能

走一遍演示环境的边界、环境变量是怎么加载的、你对 CORS 和日志的假设，再跑一个负向访问测试——全程不用打开任何一个密钥文件。

  • 最小权限：用户、服务、工具，谁都只给刚好够用的权限。
  • 数据边界：演示、预发布、生产这几个环境之间，数据和凭证都要有真正的技术隔离，不能只靠自觉。
  • 提示词/数据注入：不受信任的文档或用户输入，想方设法改变系统行为，或者把不该露的信息套出来。
  • CORS，说具体点：api/app.py 里设的是 allow_origins=["*"]——这是一个可以直接读到的事实，不是需要你去验证的假设。自己判断一下，这对这个演示环境的威胁模型来说是否可以接受，真要做成多租户的生产部署，又该怎么改。

首选阅读：OWASP — Top 10 for Large Language Model Applications

2 · 走一遍证据循环

先看摄取（ingestion）这条边界——这是空跑（dry run），不会改动任何东西：

cd demo
python3 setup_demo.py ingest --dry-run

读一下打印出来的命令，确认密钥路径是对的：.env.demo.local（仅供演示用，已加入 .gitignore）跟 demo/.env（生产环境变量的副本）是两个完全独立的文件——演示技术栈永远不会去读后者。

接下来实测查询阶段的边界。把技术栈启动起来（python3 setup_demo.py up）之后，用同一个问题、除了 workspace 字段以外完全相同的请求体，调用两次 /api/v1/qa：

curl -s -X POST http://localhost:8000/api/v1/qa \
  -H "Content-Type: application/json" \
  -d '{"question": "What changed between V3 and V4 of PR-QA-MRD-009?", "workspace": "meridian_demo"}'

curl -s -X POST http://localhost:8000/api/v1/qa \
  -H "Content-Type: application/json" \
  -d '{"question": "What changed between V3 and V4 of PR-QA-MRD-009?", "workspace": "not-a-real-workspace"}'

对比两次返回结果里的 stats.graph_context_chars 和 sources 里的引用列表。如果图谱相关的证据在两次调用之间发生了变化，甚至直接消失了，而向量/摘要/全文这几路的引用完全没变，你就亲眼看到了这条边界真实的样子：图谱信号这一路是真管用的，另外三路完全没设防。

把用到的命令、配置、跑出来的结果和失败案例都记下来；千万别拿一次实验的结果，就断言整个系统已经靠谱。

无论答案有多准确——只要暴露了受限文档或密钥，就是失败。
